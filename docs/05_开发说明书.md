# Dataspool

**副标题：下一代混合模式数据迁移与编排平台**

---

## 1. 核心架构设计：Hybrid Mode（混合模式）

为了兼顾"极简部署"与"弹性扩展"，采用 **全能节点（All-in-One）** 架构。每个 dataspool 进程实例都包含双重身份：

**Control Plane（大脑）**

- **职责**：集群管理、元数据存储（Templates, ILM, Mappings）、任务分发、API 网关。
- **高可用**：通过内置的 Raft 协议（或依赖外部 Etcd）实现多实例间的 Leader 选举，消除单点故障。

**Agent Plane（四肢）**

- **职责**：数据读取（Source）、转换（Transform）、写入（Sink）。
- **并发机制**：每个实例内置一个轻量级 Worker Pool。多实例部署时，自动组成 Worker 集群，实现任务的自动分片与抢占。

---

## 2. 关键机制：多实例如何并发迁移

当部署 3 个 Dataspool 实例（Node A, B, C）时，数据迁移的提速逻辑如下：

**任务切分（Sharding）**

1. 用户提交任务（如迁移索引 `logs-*`）。
2. Leader 节点将任务拆分为多个分片（例如：`logs-2024.01`、`logs-2024.02`、`logs-2024.03`）。

**分布式锁与抢占**

- 每个实例的内置 Agent 监听任务队列。
- Agent A 抢占分片 1，Agent B 抢占分片 2，Agent C 抢占分片 3。

**并行执行**

- 三个实例同时并行拉取数据、写入目标端。
- 结果：迁移速度理论上是单实例的 3 倍（受限于网络带宽和目标端写入能力）。

## 3. 通信与控制：gRPC + 独立 UI

### 3.1 gRPC 通信层（内部高速公路）

**Control ↔ Agent（内部）**

- **协议**：gRPC + HTTP/2
- **优势**：使用 Bidirectional Streaming 保持长连接。Leader 可以实时推送指令（如"暂停任务"），Agent 可以实时上报进度和日志，无需轮询，降低延迟。

**UI ↔ Control（外部）**

- **协议**：gRPC-Web 或 RESTful API
- **序列化**：Protobuf。定义严格的接口契约（`.proto` 文件），确保多语言客户端（Rust 后端、TypeScript 前端）的数据一致性。

### 3.2 独立 UI 架构（现代化控制台）

- **技术栈**：React 19（TypeScript），静态构建后独立部署于 Nginx / CDN。
- **连接方式**：UI 通过浏览器直接连接负载均衡器（LB）后的 Dataspool 集群。
- **功能**：
  - **集群视图**：展示所有节点（Control / Agent）的健康状态、CPU / 内存使用率。
  - **实时日志**：通过 gRPC Stream 接收并展示迁移过程中的实时日志（类似 `tail -f`）。
  - **任务编排**：可视化配置迁移任务，选择目标 Agent 组（例如："NFS 组"或"ES 组"）。

## 4. 存储层：eloqstore

存储层采用 **eloqstore**，支持两种模式无缝切换，适配从单机到云端的全场景需求：

- **本地磁盘模式**：默认使用本地文件系统存储元数据与任务状态，零外部依赖，极简部署。
- **S3 扩展模式**：当本地存储容量不足或需要跨节点共享时，自动切换至 S3 兼容的对象存储（AWS S3、MinIO 等），实现弹性扩容。
- **统一接口**：上层业务代码无需感知底层存储介质，eloqstore 提供统一的 Rust 异步 API，保证一致的读写语义。

## 5. 技术栈总览（Rust 生态）

| 层次 | 组件 | 说明 |
|------|------|------|
| 异步运行时 | [Tokio](https://tokio.rs) | 主流 Rust 异步运行时 |
| gRPC 框架 | [Tonic](https://github.com/hyperium/tonic) | Rust 原生 gRPC，基于 Tokio |
| HTTP API | [Axum](https://github.com/tokio-rs/axum) | Tokio 生态 Web 框架 |
| 序列化 | [Prost](https://github.com/tokio-rs/prost) | Protobuf 编解码（配合 Tonic） |
| Raft 共识 | [openraft](https://github.com/datafuselabs/openraft) | 生产级 Raft 实现 |
| 存储层 | [eloqstore](https://github.com/eloqdata/eloqstore) | 本地磁盘 + S3 混合存储 |
| 配置解析 | [serde](https://serde.rs) + [config-rs](https://github.com/mehcode/config-rs) | YAML 配置文件解析 |
| 日志追踪 | [tracing](https://github.com/tokio-rs/tracing) | 结构化日志与分布式追踪 |
| 前端 | React 19 + TypeScript | 独立部署，gRPC-Web 接入 |

## 6. 扩展性支持：全场景数据源

基于此架构，所有扩展功能均可无缝集成：

- **快照迁移**：作为 Agent 的一种特殊任务类型，直接读取 S3 / NFS 上的快照文件。
- **异构数据库**：通过插件化 Driver，支持 MySQL、MongoDB 等数据源。
- **文件系统**：Agent 直接读取本地 / NFS 文件，利用 Offset Tracking 实现断点续传。

---

## 7. 运行模式对比

| 模式 | 架构 | 适用场景 |
|------|------|----------|
| 纯 Server 模式 | Control (3 Nodes) + Agent (N Nodes) | 大规模生产环境。Control 专注调度，Agent 专注搬运，性能最强。 |
| **混合模式（推荐）** | Dataspool (3 Nodes) [Control + Agent] | 中小规模生产环境。部署简单，依然支持多实例并发和高可用。 |
| 独立 CLI 模式 | `dataspool run task.yaml` | 一次性任务 / 脚本。不启动 HTTP 服务，直接运行单次迁移。 |

## 8. 配置文件示例（混合模式集群）

```yaml
# dataspool-cluster.yaml

# 集群配置 (Control Plane)
cluster:
  node_name: "dataspool-node-1"
  # 集群成员列表 (用于 Raft 通信)
  peers:
    - "192.168.1.10:7000"
    - "192.168.1.11:7000"
    - "192.168.1.12:7000"
  # 选举超时时间
  election_timeout: "5s"

# 服务配置
server:
  # gRPC 端口 (供内部通信)
  grpc_port: 50051
  # HTTP 端口 (供 UI 和外部 API 调用)
  http_port: 8080

# 存储配置 (eloqstore)
storage:
  # 本地磁盘路径（默认模式）
  local_path: "/var/lib/dataspool/data"
  # S3 配置（本地不足时启用）
  s3:
    enabled: false
    bucket: "dataspool-meta"
    region: "us-east-1"
    endpoint: ""  # 留空使用 AWS，或填写 MinIO 地址

# Agent 配置 (内置 Worker)
agent:
  enabled: true
  # 资源限制 (防止拖垮 Control)
  resources:
    max_concurrent_tasks: 4  # 根据 CPU 核数调整
    memory_limit_mb: 2048
  # 标签 (用于任务路由)
  tags:
    - "hybrid-node"
    - "can-access-nfs"
```

## 9. 总结

Dataspool 以 **混合模式** 为核心架构，以 **Rust 主流开源生态** 为技术底座，以 **eloqstore** 提供本地磁盘与 S3 双模存储，以 **React 19** 构建现代化控制台，既解决了单点故障问题，又通过多实例并发实现线性提速，同时保持部署的极简性。
