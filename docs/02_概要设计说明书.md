## 2. 系统总体架构

### 2.1 架构概述

Dataspool 采用**混合模式全能节点（Hybrid All-in-One）**架构，每个进程实例同时承担 Control Plane 和 Agent Plane 两种角色。多个实例组成集群后，Control Plane 通过 Raft 协议选出 Leader 节点，Agent Plane 自动形成分布式 Worker Pool。

```
┌─────────────────────────────────────────────────────────────────┐
│                         用户界面层                               │
│         Vue/React UI  ←→  gRPC-Web / RESTful API               │
└───────────────────────────────┬─────────────────────────────────┘
                                │
            ┌───────────────────┼───────────────────┐
            │                   │                   │
    ┌───────▼────────┐  ┌───────▼────────┐  ┌───────▼────────┐
    │  Dataspool-1   │  │  Dataspool-2   │  │  Dataspool-3   │
    │ ┌────────────┐ │  │ ┌────────────┐ │  │ ┌────────────┐ │
    │ │ Control ★  │ │  │ │  Control   │ │  │ │  Control   │ │
    │ │  (Leader)  │ │  │ │ (Follower) │ │  │ │ (Follower) │ │
    │ └────────────┘ │  │ └────────────┘ │  │ └────────────┘ │
    │ ┌────────────┐ │  │ ┌────────────┐ │  │ ┌────────────┐ │
    │ │   Agent    │ │  │ │   Agent    │ │  │ │   Agent    │ │
    │ │ Worker Pool│ │  │ │ Worker Pool│ │  │ │ Worker Pool│ │
    │ └────────────┘ │  │ └────────────┘ │  │ └────────────┘ │
    └───────┬────────┘  └───────┬────────┘  └───────┬────────┘
            │     gRPC Raft     │                   │
            └───────────────────┴───────────────────┘
            │                   │                   │
    ┌───────▼──────┐   ┌────────▼──────┐   ┌────────▼──────┐
    │  Source A    │   │  Source B     │   │  Target       │
    │  (ES Cluster)│   │  (MySQL/NFS)  │   │  (ES Cluster) │
    └──────────────┘   └───────────────┘   └───────────────┘
```

### 2.2 分层架构

系统从上至下分为五个层次：

**表示层（Presentation Layer）**：独立部署的 Vue/React 前端应用，通过 Nginx/CDN 分发静态资源，经负载均衡器连接后端集群。

**API 网关层（API Gateway Layer）**：由 Control Plane 提供，暴露 RESTful API 和 gRPC-Web 接口，负责认证鉴权、请求路由、限流熔断。

**控制平面（Control Plane）**：集群的"大脑"，负责元数据管理、任务调度、Raft 共识、集群状态维护。

**执行平面（Agent Plane）**：集群的"四肢"，负责实际的数据读取（Source）、转换（Transform）、写入（Sink）操作，内置轻量级 Worker Pool。

**数据源层（Data Source Layer）**：通过插件化 Driver 对接各类数据系统（ES、MySQL、MongoDB、文件系统、S3/NFS）。

## 4. 核心机制设计

### 4.1 Raft 一致性机制

Dataspool 内置 Raft 协议（或支持对接外部 Etcd），用于：

- **Leader 选举**：集群启动后自动选出唯一 Leader，作为任务分发和元数据写入的权威节点。
- **日志复制**：任务状态变更、元数据修改等操作通过 Raft 日志在所有节点间同步，保证强一致性。
- **选举超时**：默认 5 秒，可通过 `election_timeout` 配置项调整。

关键参数：
- 集群规模建议奇数节点（3、5、7），最小可用节点数 = ⌊N/2⌋ + 1。
- 3 节点集群可容忍 1 节点故障，5 节点集群可容忍 2 节点故障。

### 4.2 任务分片与并发执行

任务分片流程：

1. 用户提交任务（如迁移 `logs-*` 索引）。
2. Leader 的 Scheduler 根据数据源特征自动拆分为多个 Shard（如按月份索引 `logs-2024.01`、`logs-2024.02` …）。
3. Shard 信息写入 Raft 日志，同步至所有节点。
4. 各节点 Agent 监听 Shard 队列，通过分布式锁（基于 Raft KV）进行抢占。
5. 各 Agent 并行执行所抢占的 Shard，实时上报进度至 Leader。

分片策略（可配置）：
- **按索引名**（ES）：每个索引名一个 Shard。
- **按日期范围**：按天/周/月拆分。
- **按主键范围**（MySQL）：按 ID 范围均匀切分。
- **按文件**（文件系统）：每个文件一个 Shard。

### 4.3 断点续传机制

每个 Shard 在执行过程中持续更新 Offset 状态：

- ES Source：记录已迁移的 Scroll ID 和文档数。
- MySQL Source：记录已迁移的最大主键值或 Binlog 位置。
- 文件系统 Source：记录已读取的文件字节偏移量。

Offset 状态通过 Raft 日志持久化，节点重启或故障切换后从最新 Offset 继续执行。

### 4.4 资源隔离机制

Agent 内置资源控制：
- `max_concurrent_tasks`：限制单 Agent 最大并行 Shard 数，默认根据 CPU 核数设置。
- `memory_limit_mb`：限制 Agent 使用的内存上限，超出时暂停新 Shard 的执行。
- 读取速率限制（Rate Limiting）：防止源端集群过载。

## 5. 通信架构

### 5.1 内部通信（Control ↔ Agent）

- **协议**：gRPC + HTTP/2
- **模式**：双向流（Bidirectional Streaming）
- **功能**：
  - Control → Agent：推送任务指令（分配、暂停、取消 Shard）
  - Agent → Control：上报任务进度、实时日志、资源使用率
- **安全**：支持 mTLS 双向认证（生产环境必须开启）

### 5.2 外部通信（UI/Client ↔ Control）

- **协议**：HTTP/1.1 + JSON（RESTful API）或 gRPC-Web + Protobuf
- **端口**：HTTP 8080，gRPC 50051
- **认证**：JWT Token（有效期 24h）+ API Key（长期凭证）
- **实时推送**：Server-Sent Events（SSE）或 WebSocket，用于日志流和进度更新

### 5.3 Protobuf 核心接口定义

主要 .proto 文件：

- `cluster.proto`：节点注册、健康上报、集群状态查询
- `task.proto`：任务创建、Shard 分配、进度上报、任务控制（暂停/恢复/取消）
- `log.proto`：实时日志流
- `meta.proto`：元数据 CRUD（Templates、Mappings、ILM）

## 6. 部署架构

### 6.1 混合模式（推荐，中小规模）

```
负载均衡器（LB）
      │
      ├── Dataspool Node-1 (8080/50051) [Control+Agent]
      ├── Dataspool Node-2 (8080/50051) [Control+Agent]
      └── Dataspool Node-3 (8080/50051) [Control+Agent]

UI (Nginx/CDN) ──► LB ──► Dataspool Cluster
```

三个节点均可对外提供 API 服务，UI 通过 LB 访问集群，读请求可在所有节点负载均衡，写请求由 LB 转发至 Leader。

### 6.2 纯 Server 模式（大规模）

```
Control Cluster (3 Nodes) ◄──► Agent Pool (N Nodes)
        │
        ▼
   LB / API Gateway
        │
       UI
```

Control 节点专注于调度与元数据管理，Agent 节点可按需水平扩展至数十个，最大化迁移吞吐量。

### 6.3 容器化部署

- 提供官方 Docker 镜像。
- 提供 Helm Chart，支持在 Kubernetes 上以 StatefulSet 方式部署 Control 节点，以 DaemonSet 或 Deployment 方式部署 Agent 节点。

## 7. 技术选型

| 层次 | 技术选择 | 选型理由 |
|------|----------|----------|
| 后端语言 | Rust | 高性能、内存安全、零成本抽象，适合高并发 I/O 密集型场景 |
| 前端框架 | Vue 3 / React 18 | 生态成熟，组件丰富，支持响应式数据绑定 |
| RPC 框架 | gRPC（tonic-rs） | 高性能、强类型、双向流支持，适合微服务通信 |
| 序列化协议 | Protobuf 3 | 紧凑高效，多语言支持，强类型契约 |
| 一致性协议 | Raft（openraft） | 成熟可靠，可嵌入，无外部依赖 |
| 本地 KV 存储 | RocksDB / sled | 嵌入式高性能 KV，用于元数据和 Offset 持久化 |
| 配置格式 | YAML | 易读易写，广泛支持 |
| 监控指标 | Prometheus | 行业标准，与 Grafana 生态完善对接 |
| 日志格式 | JSON 结构化日志 | 便于 ELK/Loki 等日志系统采集与查询 |
| 容器化 | Docker + Helm | 标准化部署，便于 Kubernetes 集成 |

## 8. 关键设计决策

### 8.1 为何选择混合模式作为推荐架构

纯 Control/Agent 分离模式虽然性能最优，但部署复杂度较高，对中小规模用户不友好。混合模式通过"全能节点"设计，在三节点的情况下同时获得高可用保障和多节点并发加速，是性能与简洁性的最佳平衡。

### 8.2 为何内置 Raft 而非依赖外部 Etcd

内置 Raft 可将 Dataspool 做成单二进制文件，零外部依赖即可启动，极大降低了部署门槛。同时，系统保留了对外部 Etcd 的支持，供有更高定制需求的用户选择。

### 8.3 为何采用插件化 Driver 架构

数据源种类繁多且持续扩展，将驱动层设计为插件化接口，新增数据源支持时无需修改核心调度逻辑，降低了耦合度，提高了可维护性和可扩展性。

### 8.4 UI 与后端独立部署的优势

前后端分离部署使得 UI 可以独立更新发布，不影响后端集群。同时，静态 UI 可部署至 CDN，提升全球访问速度，并减少后端服务的 HTTP 静态资源压力。
