## 1. 引言

### 1.1 编写目的

本文档描述 Dataspool 系统的数据持久化方案，包括内嵌 KV 存储（RocksDB）的键空间设计、关系型数据模型（可选启用）、数据生命周期管理策略，以及数据备份与恢复机制。

### 1.2 存储引擎选择说明

Dataspool 默认采用 **内嵌式 RocksDB** 作为持久化存储引擎，原因如下：

- 零外部依赖，随进程启动，无需额外部署数据库服务；
- 高性能顺序写入，适合 Raft 日志追加场景；
- 支持 Column Families，可对不同数据类型分别调优；
- 原生支持 Snapshot，便于 Raft 快照压缩。

对于需要复杂查询（如按时间范围查询历史任务）的场景，系统提供可选的 **PostgreSQL 对接模式**，将任务历史数据异步同步至关系型数据库，以支持丰富的 SQL 查询。

## 3. Raft 状态机存储设计（RocksDB）

RocksDB 中通过 Column Family（CF）隔离不同类型的数据，每个 CF 独立配置压缩、缓存等参数。

### 3.1 Column Family 总览

| CF 名称 | 用途 | 预估数据量 | 读写模式 |
|---------|------|-----------|----------|
| `raft` | Raft 日志条目、HardState、投票记录 | 中（定期压缩） | 频繁顺序写 |
| `meta` | 任务、分片、节点、模板、Mapping 等元数据 | 小–中 | 随机读多写少 |
| `offset` | Shard 断点续传进度 | 中 | 频繁随机写 |
| `auth` | 用户账号、API Key、角色权限 | 小 | 读多写少 |
| `alert` | 告警规则、告警历史 | 小 | 读多写少 |

### 3.2 CF: raft（Raft 引擎专用）

由 openraft 框架直接管理，存储以下内容：

```
Key 格式:
  raft:log:{index:020}         → Raft 日志条目（Protobuf 编码）
  raft:hard_state              → HardState（current_term, voted_for, commit）
  raft:snapshot_meta           → 最新 Snapshot 元数据
  raft:membership              → 集群成员配置
```

配置建议：

```
write_buffer_size: 64MB
level0_file_num_compaction_trigger: 4
compression: Lz4
```

## 4. 关系型数据（可选 PostgreSQL）

当启用 PostgreSQL 对接时，系统将任务历史和审计日志异步写入以下表结构，支持复杂查询和报表生成。

### 4.1 tasks_history 表

```sql
CREATE TABLE tasks_history (
    id              UUID            PRIMARY KEY,
    name            VARCHAR(255)    NOT NULL,
    description     TEXT,
    source_type     VARCHAR(64)     NOT NULL,
    sink_type       VARCHAR(64)     NOT NULL,
    state           VARCHAR(32)     NOT NULL,
    created_by      VARCHAR(128)    NOT NULL,
    created_at      TIMESTAMPTZ     NOT NULL,
    updated_at      TIMESTAMPTZ     NOT NULL,
    started_at      TIMESTAMPTZ,
    finished_at     TIMESTAMPTZ,
    duration_secs   INTEGER,
    total_shards    INTEGER         DEFAULT 0,
    completed_shards INTEGER        DEFAULT 0,
    failed_shards   INTEGER         DEFAULT 0,
    docs_read       BIGINT          DEFAULT 0,
    docs_written    BIGINT          DEFAULT 0,
    bytes_read      BIGINT          DEFAULT 0,
    bytes_written   BIGINT          DEFAULT 0,
    error_message   TEXT,
    config_snapshot JSONB           -- 任务配置快照，便于回溯
);

CREATE INDEX idx_tasks_state ON tasks_history(state);
CREATE INDEX idx_tasks_created_at ON tasks_history(created_at DESC);
CREATE INDEX idx_tasks_created_by ON tasks_history(created_by);
CREATE INDEX idx_tasks_source_type ON tasks_history(source_type);
```

### 4.2 shards_history 表

```sql
CREATE TABLE shards_history (
    id              UUID            PRIMARY KEY,
    task_id         UUID            NOT NULL REFERENCES tasks_history(id),
    seq             INTEGER         NOT NULL,
    spec            JSONB           NOT NULL,   -- 分片规格（索引名等）
    state           VARCHAR(32)     NOT NULL,
    assigned_node   VARCHAR(128),
    attempt_count   INTEGER         DEFAULT 0,
    started_at      TIMESTAMPTZ,
    completed_at    TIMESTAMPTZ,
    duration_secs   INTEGER,
    docs_processed  BIGINT          DEFAULT 0,
    bytes_processed BIGINT          DEFAULT 0,
    last_error      TEXT
);

CREATE INDEX idx_shards_task_id ON shards_history(task_id);
CREATE INDEX idx_shards_state ON shards_history(state);
CREATE INDEX idx_shards_node ON shards_history(assigned_node);
```

### 4.3 audit_logs 表

```sql
CREATE TABLE audit_logs (
    id              BIGSERIAL       PRIMARY KEY,
    event_time      TIMESTAMPTZ     NOT NULL DEFAULT NOW(),
    user_id         VARCHAR(128)    NOT NULL,
    action          VARCHAR(64)     NOT NULL,  -- task:create, task:cancel, node:remove ...
    resource_type   VARCHAR(64)     NOT NULL,
    resource_id     VARCHAR(128),
    request_id      UUID,
    client_ip       INET,
    success         BOOLEAN         NOT NULL,
    error_message   TEXT,
    details         JSONB           -- 额外上下文信息
);

CREATE INDEX idx_audit_event_time ON audit_logs(event_time DESC);
CREATE INDEX idx_audit_user_id ON audit_logs(user_id);
CREATE INDEX idx_audit_action ON audit_logs(action);
```

## 6. KV 键空间设计

### 6.1 键命名规范

所有键遵循 `{namespace}:{entity_type}:{identifier}` 的三级前缀结构，具体规则如下：

- 命名空间（namespace）：`raft`、`meta`、`offset`、`auth`、`alert`
- 实体类型（entity_type）：`task`、`shard`、`node`、`template`、`user`、`apikey`、`role` 等
- 标识符（identifier）：UUID v4（主键）或可读字符串

### 6.2 完整键空间一览

```
raft:log:{index:020}                    → Raft 日志条目
raft:hard_state                         → Raft HardState
raft:snapshot_meta                      → 快照元数据
raft:membership                         → 成员配置

meta:task:{task_id}                     → 任务元数据
meta:task_by_state:{state}:{task_id}    → 按状态查询辅助键
meta:task_by_user:{user_id}:{task_id}   → 按用户查询辅助键
meta:task_by_time:{ts}:{task_id}        → 按时间排序辅助键

meta:shard:{shard_id}                   → 分片元数据
meta:shard_by_task:{task_id}:{shard_id} → 按任务查询辅助键
meta:shard_by_state:{state}:{shard_id}  → 按状态查询辅助键（查找 Pending Shard）
meta:shard_by_node:{node_id}:{shard_id} → 按节点查询辅助键（故障恢复）

meta:node:{node_id}                     → 节点信息
meta:template:{template_id}             → 任务模板
meta:mapping:{mapping_name}             → ES 字段映射配置

offset:{shard_id}                       → 断点续传进度

auth:user:{user_id}                     → 用户账号
auth:user_by_name:{username}            → 用户名索引
auth:apikey:{key_id}                    → API Key
auth:role:{role_name}                   → 角色定义

alert:rule:{rule_id}                    → 告警规则
alert:history:{alert_id}               → 告警历史记录
```

## 7. 数据生命周期管理

### 7.1 Raft 日志压缩

Raft 日志会随时间持续增长。系统每当日志条目数达到 `snapshot_interval`（默认 10,000）时，自动触发快照（Snapshot）操作：将当前状态机状态序列化为快照文件，并删除快照点之前的日志条目，防止磁盘无限增长。

### 7.2 已完成任务的清理策略

```yaml
data_retention:
  completed_tasks_keep_days: 30      # 已完成任务保留 30 天
  failed_tasks_keep_days: 90         # 失败任务保留 90 天（便于问题排查）
  offset_keep_after_completion: 7    # 任务完成后 Offset 记录保留 7 天
  audit_logs_keep_days: 365          # 审计日志保留 1 年
```

清理任务由 Leader 节点每日凌晨执行，通过 Raft 日志广播删除操作至所有节点。

### 7.3 存储容量估算

| 数据类型 | 单条大小估算 | 日增量估算 | 1年总量估算 |
|----------|-------------|-----------|------------|
| 任务元数据 | 2 KB | 100 条 | 73 MB |
| 分片记录 | 500 Bytes | 1,000 条 | 183 MB |
| Offset 记录 | 200 Bytes | 1,000 条 | 73 MB |
| Raft 日志 | 200 Bytes | 10,000 条（压缩后 ~1,000 条存留） | <10 MB |
| 审计日志 | 300 Bytes | 10,000 条 | 1 GB |

生产环境建议为 `/var/lib/dataspool` 分配至少 **50 GB** 存储空间。

## 8. 数据备份与恢复

### 8.1 热备份（在线）

```bash
# 使用 RocksDB Checkpoint API 创建热备份（不中断服务）
dataspool admin backup --output /backup/dataspool-$(date +%Y%m%d)
```

备份内容：RocksDB 的全量 Checkpoint（所有 SST 文件的硬链接）。

### 8.2 冷备份（离线）

```bash
# 停止服务后直接压缩 data_dir
tar -czf dataspool-backup.tar.gz /var/lib/dataspool/
```

### 8.3 数据恢复

```bash
# 从备份目录恢复（恢复前需停止服务）
dataspool admin restore --input /backup/dataspool-20260213
```

### 8.4 Raft 快照导出

对于 3 节点集群，Leader 节点的 Raft 快照即为集群状态的完整副本，可通过以下命令导出供离线分析：

```bash
dataspool admin export-snapshot --output snapshot.json
```

## 9. 性能考量

### 9.1 RocksDB 调优参数

```
# 写入优化（适合 Offset 频繁更新场景）
write_buffer_size = 128MB         # 单个 Memtable 大小
max_write_buffer_number = 3       # 同时在内存中的 Memtable 数量
level0_slowdown_writes_trigger = 20
level0_stop_writes_trigger = 36

# 读取优化（适合元数据随机读）
block_cache_size = 512MB          # LRU Block Cache
bloom_filter_bits_per_key = 10    # Bloom 过滤器，减少无效磁盘读取

# 压缩
compression = lz4                 # L0/L1 层使用 LZ4
bottommost_compression = zstd     # 底层使用 ZSTD，压缩率更高
```

### 9.2 热点键规避

Offset 写入是系统中频率最高的写操作（每 30s 或每 10,000 条记录一次）。为避免 RocksDB 写入热点，Offset CF 的键以 Shard ID（UUID）为前缀，天然分散写入压力。

### 9.3 PostgreSQL 连接池配置（可选模式）

```yaml
postgres:
  url: "postgresql://dataspool:${PG_PASSWORD}@pg-host:5432/dataspool"
  max_connections: 20
  min_connections: 2
  connect_timeout_secs: 5
  idle_timeout_secs: 300
  async_write: true              # 异步写入，不阻塞主流程
  batch_insert_size: 100         # 批量插入 tasks_history 的批次大小
```
